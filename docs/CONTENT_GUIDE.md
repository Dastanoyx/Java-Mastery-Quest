# Content Authoring Guide

All educational content lives in `content/` and is plain text, reviewed like code.

```
content/
  blueprint.yaml               exam format + domains + objectives (IDs D1.1 … D10.1)
  achievements.yaml
  lessons/D3/03-constructors.md
  questions/D3-oop.yaml        (any number of YAML files; each is a list)
  exercises/D3-oop.yaml
  .verification/java-results.json   ← generated by content:verify-java, committed
```

Workflow: edit → `npm run content:validate` → `npm run content:verify-java -- --only D3` → `npm run seed`.
Nothing is shown as "JDK-verified" unless its current hash passed verification on JDK 25.

## 1. Lessons (Markdown + front matter)

```markdown
---
id: oop-constructors                 # stable, kebab-case, never renamed
domain: D3
order: 3                             # mission order within the domain (unique)
title: Constructors, Initialization Order & Flexible Constructor Bodies
summary: One or two sentences shown on cards.
minutes: 45
objectives: [D3.2]
prerequisites: [oop-classes-objects]
contract:                            # Part A — learning contract (≥2)
  - Predict the exact order in which static/instance initializers and constructors run.
keyRules:                            # shown in the side panel and Knowledge Vault (≥2)
  - "`this(...)` and `super(...)` can only appear once, and only in a constructor."
retrieval:                           # Part I — recall prompts without looking (≥1)
  - Write the initialization order for `new Child()` from memory.
checks: [D3-CTR-001]                 # extra knowledge checks shown at the end of sections
mastery: [D3-CTR-010, D3-CTR-011, D3-CTR-012]   # final mastery quiz (≥3, NOT reused in checks)
---

## Mental model          ← every lesson has ≥3 `##` sections; they form the outline
...
```

### Interactive blocks

| Syntax | Renders as |
|---|---|
| ```` ```java predict ```` followed immediately by ```` ```output ```` | "Predict the output" card: learner writes a guess, then reveals. **The code must be a complete program** — it is compiled and run on JDK 25 and the output block must match exactly. If the program throws, end the output with `Exception in thread "main" java.lang.X: message`. If it must not compile, the output block starts with `Compilation fails` (still verified). |
| ```` ```java ```` | Static, syntax-highlighted code (fragments allowed, not executed). |
| `::check D3-CTR-001` (own line) | Inline knowledge-check question (learning mode, instant feedback). |
| `::exercise D3-EX-001` (own line) | Embedded coding exercise (runs in the sandbox). |
| `> [!RULE]`, `> [!TRAP]`, `> [!NOTE]`, `> [!J25]`, `> [!TIP]`, `> [!REAL]` | Callouts: language rule, exam trap, note, Java-25-specific, tip, real-world. |

Raw HTML is not rendered (XSS-safe). Tables (GFM) are supported.

### Teaching standard (Parts A–J)

A: contract (front matter) · B: mental model from first principles · C: syntax & exact rules, compile-time vs
runtime · D: code walkthrough with predict blocks · E: "what if" variations, one change at a time ·
F: exam traps (`[!TRAP]`) · G: guided practice (`::check`, `::exercise`) · H: mastery quiz (front matter) ·
I: retrieval prompts (front matter) · J: completion is handled by the app. Mark Java-25-only behaviour with
`[!J25]` and say which JEP. Mark supplementary (non-exam) material clearly with `> [!NOTE] Beyond the exam`.

## 2. Questions (YAML)

```yaml
- id: D3-OVL-004                 # D<domain>-<TOPIC>-<nnn>, unique, never reused
  objective: D3.3
  lesson: oop-overloading        # remediation lesson
  type: single                   # single | multi | text
  format: overload-resolution    # concept | predict-output | does-it-compile | compile-error | runtime-exception
                                 # | select-valid | overload-resolution | polymorphism | trace | repair | complete | short-answer
  difficulty: advanced           # foundation | intermediate | advanced | expert   (reasoning depth, not code length)
  estSeconds: 120
  tags: [overloading, boxing, varargs]
  prompt: What is the output of the following program?
  code: |
    public class Main {
        static void m(long x)     { System.out.print("long "); }
        static void m(Integer x)  { System.out.print("Integer "); }
        static void m(int... x)   { System.out.print("varargs "); }
        public static void main(String[] args) { m(5); }
    }
  options:
    - { key: a, text: "`long`", correct: true, why: "Phase 1 (no boxing, no varargs) finds m(long) via widening int→long." }
    - { key: b, text: "`Integer`", why: "Boxing is only considered in phase 2, after phase 1 already found m(long)." }
    - { key: c, text: "`varargs`", why: "Varargs is phase 3, the last resort." }
    - { key: d, text: "Compilation fails: ambiguous call", why: "Phases are tried in order; the first phase that applies wins, so there is no ambiguity." }
  explanation: |
    Overload resolution (JLS §15.12.2) runs in three phases ...
  rule: "JLS 15.12.2: phase 1 = widening only; phase 2 = + boxing/unboxing; phase 3 = + varargs."
  misconception: "\"Integer matches int best because it's the same type family.\""
  hint: Which conversions are allowed in the first phase?
  examEligible: true             # false for text/coding-style questions or practice-only formats
  java:                          # REQUIRED whenever there is code
    expect: { compiles: true, stdout: "long" }
```

Rules:

- **Every option has a `why`.** Wrong-option explanations name the misconception they model.
- **Any question with code needs a `java` block** (or per-option `java` blocks for "which compiles?"
  questions). `source:` may hold a fuller program than the displayed `code` (e.g. adding a `main`), but the
  displayed code must not differ in behaviour-relevant ways.
- For `predict-output` single-choice questions, the correct option text (backticks stripped) must equal the
  real stdout exactly; for multi-line output use a YAML block string in `text`. The verifier enforces this
  and also checks that no wrong option accidentally equals the real output.
- `expect.compiles: false` → add `errorContains` (a fragment of javac's English message) and, if the question
  asks *which line*, `errorLine`.
- Uncaught exceptions → `expect.exception: java.lang.ClassCastException`.
- Never write nondeterministic programs as if they were deterministic (thread interleaving, `HashSet`
  iteration order of non-trivial types, `parallel()` + `forEach`). Use `stdoutContains` or restructure.
- Do not reproduce questions from commercial banks, books or "dumps". Write original items.
- `difficulty` reflects reasoning steps: foundation = one rule; intermediate = two interacting rules;
  advanced = three+ rules or a subtle edge case; expert = the classic exam trap that most experienced
  developers get wrong.
- Concept questions without code get `verification: reviewed` automatically and display as
  "Concept · reviewed" rather than "JDK-verified".

## 3. Coding exercises (YAML)

```yaml
- id: D3-EX-001
  objective: D3.2
  lesson: oop-constructors
  title: Validated temperature record
  difficulty: intermediate
  kind: implement                # implement | repair | complete
  prompt: |
    Implement `Temperature` as a record ... (Markdown)
  fileName: Solution.java         # learner edits this file (it may declare several top-level types)
  starter: |
    record Temperature(double celsius) { /* TODO */ }
    class Solution {}
  solution: |
    ...
  harness: |                      # hidden Main.java; prints one line per test
    public class Main {
      static void t(String name, boolean ok) { System.out.println((ok ? "PASS " : "FAIL ") + name); }
      public static void main(String[] a) { ... }
    }
  explanation: Why the reference solution works.
  hints: [ "Use a compact canonical constructor." ]
```

The verifier requires the reference solution to pass every test and the starter to fail at least one.

## 4. Special verification modes

**Resource bundles (D10).** A `java` check may add `.properties` files to `files:`; the runner copies them onto
the run classpath (they are never compiled). Names must be flat, e.g. `Messages_fr_CA.properties`.

```yaml
java:
  files:
    - { name: Labels.properties,    content: "greet=Hello\nbye=Bye\n" }
    - { name: Labels_fr.properties, content: "greet=Bonjour\n" }
  expect: { compiles: true, stdout: "Bonjour Bye" }
```

The runner JVM uses `-Duser.language=en -Duser.country=US -Duser.timezone=UTC`, so `Locale.getDefault()` is
`en_US`. Remember the default-locale fallback step of `ResourceBundle.getBundle` when you design a question.

**Modules (D7).** Set `modules: true`; `files:` then use paths under a module source root and the verifier
compiles them locally with `javac --module-source-path` on JDK 25 (authoring-time only — never learner code).
Set `mainModule: app/app.Main` to also run it. Optional `javacArgs` / `javaArgs` (e.g. `--add-opens`).

```yaml
java:
  modules: true
  mainModule: app/app.Main
  files:
    - { name: lib/module-info.java,     content: "module lib { exports lib.api; }" }
    - { name: lib/lib/api/Api.java,     content: "package lib.api; public class Api { ... }" }
    - { name: app/module-info.java,     content: "module app { requires lib; }" }
    - { name: app/app/Main.java,        content: "package app; public class Main { ... }" }
  expect: { compiles: true, stdout: "..." }
```

Show the learner every relevant file in `code:` using `// file: lib/module-info.java` header comments.
Command-line behaviour that cannot be executed by the verifier (`jar`, `jlink`, `jdeps`, launcher flags) is
taught in lessons and assessed with `concept` questions (`verification: reviewed`), never presented as
JDK-verified.
